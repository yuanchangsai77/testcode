# 未来平台蓝图

## 状态与用途

本目录描述 `testcode`、API Control Board（`~/test`）和未来 Device Fabric 组合后的长期方向。
它是探索性设计，不表示对应能力已经实现，也不承诺当前示例会直接成为最终 API。

当前行为以 [testcode 总体架构](../architecture.md)和各专项文档为准；近期优先级以
[testcode 路线图](../roadmap.md)为准。未来设计不能绕过当前已建立的安全、能力激活、日志和
上下文预算边界。

## 设计成熟度

本目录使用三种成熟度理解设计内容：

- **不变量**：跨实现应长期保持的原则，例如状态单一所有者、能力执行必须经过统一 policy。
- **当前推荐**：在现有信息下最合适的结构，可以在验证后调整，例如先使用出站长连接接入设备。
- **候选方案**：需要按性能、平台限制或部署环境选择，例如 WebSocket、MQTT、WebRTC 或对象存储。

除明确标记为不变量的内容外，模块拆分、进程数量、传输方式、字段名称和存储实现都允许演进。
进入实现阶段的稳定字段必须迁移到 `docs/reference/`，并由契约测试保护；本目录只保留最小语义。

正文使用以下显式标记，避免把候选方案误读成稳定契约：

- `[不变量]`：违反后会破坏状态所有权、安全或恢复语义。
- `[当前推荐]`：首个纵向闭环默认采用，验证结果可以推翻。
- `[候选]`：尚未选定的实现，必须通过目标环境数据比较。

未带标记的段落用于解释概念；其中的“必须”“不得”应能追溯到本目录的不变量或专项文档。关键
选择记录在下方决策记录中，变更时同时更新证据和重新评估条件。

## 总体结论

平台使用三个横向 Plane 和七层垂直 Layer：

```text
Agent Plane   任务理解、持续会话、工作流、安全执行和恢复
Model Plane   模型协议、Provider 路由、密钥、额度和健康状态
Device Plane  设备身份、能力、状态、调度、执行和数据协调

L6 Experience
L5 Composition
L4 Intelligence
L3 Orchestration
L2 Contract
L1 Runtime & Adapter
L0 Infrastructure
```

Plane 回答状态与部署归属，Layer 回答依赖方向。具体模型只是可替换推理资源；稳定的 Personal
Assistant Runtime 持有 Conversation、Workflow、Event 和授权状态。

核心原则是：

> 设备是能力载体，项目是能力与策略的组合，运行时负责形成和恢复工作流，调度器负责选择执行节点，模型网关负责选择 Provider。

## 设计不变量

1. 新能力进入统一能力仓库；存在、激活、授权、调度和执行相互分离。
2. 本地、MCP、A2A 和设备能力都经过统一 schema、policy、approval、logging 和结果路径。
3. 每类状态只有一个权威所有者，其他组件只持有投影或引用。
4. 模型不拥有持续会话、后台工作流、设备状态或用户凭据。
5. 控制消息不承载无界大数据，大型媒体和制品使用独立数据面。
6. 自动恢复不能扩大用户原有授权，物理副作用必须支持幂等或明确 reconciliation。
7. 外部内容、观察证据和模型推断不自动获得执行权限。
8. Dashboard 只聚合 API，不直接拥有其他平面的领域状态。
9. 同进程模块优先使用内部接口，不为“统一”强制引入网络协议。
10. 先验证真实纵向闭环，再按生命周期、信任域和伸缩需求拆服务。
11. 框架不枚举具体业务功能；能力、实体类型和工作流由 manifest、Profile、Plugin 与运行时发现
    动态提供，策略由可验证的 Policy Source 提供，AI 在这些受控边界内组合。
12. 经验不是权限，偏好不能扩大 Policy；模型只产生候选和使用只读投影，长期记录由运行时管理。

## 动态扩展原则

未来平台固定的是“如何描述、发现、授权、组合、执行和恢复能力”，不是固定一组设备或产品功能。
参考场景中的摄像头、投喂、环境控制、资讯和 Coding 都只是普通能力实例，不进入通用框架的必选
模块、固定枚举或默认策略。

动态不等于无契约：AI 可以根据当前能力 manifest 和上下文生成 Workflow、选择实现与调整执行
路径，但运行时仍负责 schema 校验、Policy、预算、状态机、幂等、授权和结果验证。
